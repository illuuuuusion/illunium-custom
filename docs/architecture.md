# Architektur

Eine Paper-JAR, intern getrennte Module mit explizitem Vertrag (`core.module.FeatureModule`) und einer festen Registry (`core.module.Modules`). Reihenfolge: `recipes`, `groups`, `marriage`, `playtime`, `whitelistguard`, `whiteliststaging`, `sit`, `vanish`, `spawn`, `leaderboard`. Module sprechen nicht gegenseitig SQL und rufen keine fremden Commands auf; gemeinsame Dienste kommen über `ModuleContext`; die Registry injiziert zusätzlich den read-only `PlaytimeReadService` in das Leaderboard-Modul.

```text
Paper events / commands
        │
Feature Commands/Listener ──► Feature Service (Regeln, Policy)
                                   ├──► Database (SQLite, eigener Thread)
                                   └──► AppearanceService (nur Daten melden)
                                              └──► Haupt-Scoreboard / Tablist
```

## Kern

- **Bootstrap** (`IlluniumCustomPlugin`): Config laden/validieren → SQLite öffnen + migrieren → `PlayerIdentityService` → Module in Registry-Reihenfolge aktivieren → `/ic` registrieren. Jeder Fehler deaktiviert das **ganze** Plugin (kein Teilstart). Disable: Module in umgekehrter Reihenfolge, danach DB-Queue abarbeiten und schließen.
- **Storage** (`storage.Database`): eine SQLite-Connection auf einem eigenen Thread (`IlluniumCustom-DB`); `transaction(work)` läuft geordnet, committet oder rollt zurück und liefert ein `CompletableFuture`. In `work` **keine** Bukkit-API; Folgeschritte mit `.thenAcceptAsync(..., context.mainThread())` zurück auf den Server-Thread. Nur Startup blockiert auf Storage.
- **Migrationen**: `src/main/resources/db/migrations/V<n>__*.sql`, in `Database.MIGRATIONS` angehängt. Ausgelieferte Skripte nie ändern, sondern neue additive Migration. Ein neueres Schema als bekannt oder kollidierende Tabellen brechen den Start ab; es wird nichts gelöscht.
- **Identitäten**: UUID ist die Identität, `last_known_name` wird beim Join aktualisiert. `findByName` kann bei Namenswechseln mehrere UUIDs liefern.
- **Mutationen** (Muster aus `groups`): Der Service prüft alle Regeln **in** der Transaktion gegen den committeten Zustand und lädt die betroffene Zeile im selben Commit neu; der In-Memory-Stand wird erst danach auf dem Main Thread ersetzt. Gleichzeitige Commands laufen dadurch geordnet und hinterlassen keine halben Änderungen; Constraints in der DB sind die zweite Sicherung. Regelverstöße sind `UserException` (Text geht an den Spieler), `context.reply(...)` liefert Erfolg/Fehler auf dem Main Thread aus und loggt alles andere als `SEVERE`.
- **Appearance** (`appearance.AppearanceService`, Core-Service vor den Modulen): einziger Eigentümer von Nametag/Tablist. Module melden nur Daten (`setPrefix` = Nametag + Tablist, `setSuffix` = nur Tablist) für Online-Spieler; Offline-Meldungen werden ignoriert, Module melden beim Join erneut. Jede Änderung rendert genau einen Spieler und nur, wenn sich der Wert geändert hat. Entscheidung: **Haupt-Scoreboard** (alle Zuschauer sehen dasselbe, keine per-Viewer-Boards nötig), ein Team `illuniumcustom_<uuid>` pro Spieler mit Prefix; in der Tablist ein expliziter `playerListName` (Prefix + Name + Suffix). Der Vanilla-Client zeigt bei gesetztem Tablist-Namen die Team-Dekoration nicht zusätzlich an, daher kein doppelter Tag. Das Haupt-Scoreboard wird mit der Welt gespeichert, deshalb räumt der Start alle eigenen Teams auf.
- **Visibility** (`core.VisibilityService`, Core-Service): ob andere Spieler wissen dürfen, dass jemand online ist. Ohne Vanish-Modul ist jeder sichtbar. Einziger Schreiber ist `vanish` (`setHidden`, Listener bei jeder Änderung; `forget` beim Quit ohne Benachrichtigung, damit kein „online“-Herz aufblitzt). Module zeigen Anwesenheit (Herzen, Completions, „online“) nur über `isPubliclyVisible`/`publiclyOnline`, nie über Vanish-Interna. Vanish steuert nur die Sichtbarkeit pro Zuschauer (`hidePlayer`), nie Text; Appearance bleibt Single Writer für Nametag/Tablist-Text, und CraftBukkit schickt Tablist-Namen nur an Zuschauer, die den Spieler sehen dürfen.
- **Flüchtige Anfragen** (Einladungen, Bestätigungen): `core.ExpiringMap`, gültig solange `jetzt < erstellt + TTL`, nur Main Thread, kein Persistieren.


## Grenzen

- **Kein Hot-Reload.** Paper 26.3 hat kein `/reload` mehr; ein Disable/Enable zur Laufzeit (z. B. durch Plugin-Manager) scheitert an der Command-Registrierung. Das Plugin meldet das als `ERROR`, deaktiviert sich und räumt seine Rezepte auf. Änderungen immer per Server-Neustart.


## Module mit Weltzustand

- **Whitelist Guard** (`whitelistguard`): kein eigener Speicher. `WhitelistGuard.check()` läuft beim Start und per Bukkit-Timer auf dem Main Thread, liest und setzt nur `Server#hasWhitelist`/`isWhitelistEnforced` und `OfflinePlayer#isWhitelisted` der verifizierten Staff-UUIDs. Die Mojang-Prüfung (`PlayerProfile#update`, async) läuft einmal pro Start; ihr Ergebnis wird über `context.mainThread()` übernommen. Ohne Verifikation wird nie eingetragen.
- **Sit** (`sit`): flüchtiger Zustand `Map<Spieler-UUID, Seat>` auf dem Main Thread; Eintrag vorhanden = `SITTING`. Sitz = unsichtbarer Marker-ArmorStand mit PDC-Tag `illuniumcustom:seat` und `persistent=false` (wird nie mit dem Chunk gespeichert). Aufräumen: Disable, Quit (vor dem Speichern der Spielerdaten), Tod, Teleport, Weltwechsel, Schaden, Dismount, Entity-Unload; Orphans (z. B. nach Absturz als Fahrzeug in den Spielerdaten) beim Start, Entity-Load und Join. Gelöscht werden nur ArmorStands mit unserem Tag.
- **Vanish** (`vanish`): kein Speicher, Zustand in `VisibilityService`. Unveränderliche, strikt geprüfte UUID-Policy aus der Modulkonfiguration (`true` als Kompatibilitätsdefault); sie beeinflusst nur automatische OP-Joins und den Startup-Abgleich schon anwesender Spieler. Join-Listener mit `LOWEST`, damit der Spieler vor dem Versand von Join-Nachricht und Tablist-Eintrag verborgen ist (beides prüft `canSee`). OP-Entzug wird mangels Event jede Sekunde geprüft. Der Serverlisten-Ping kann off-thread laufen und liest nur die thread-sichere Kopie `hidden()`.
- **Spawn** (`spawn`): `SpawnService` enthält alle Regeln ohne Bukkit-Aufrufe (Zustände `IDLE → WARMING_UP → COMPLETING → COOLDOWN`, Main Thread). Warmup und Combat-Tag (`ExpiringMap`) laufen auf einer monotonen Uhr und sind flüchtig; Cooldowns sind Epoch-Deadlines in `spawn_cooldowns` (Schema v2), beim Start einmal geladen (abgelaufene Zeilen gelöscht) und danach nur geschrieben, nie auf dem Main Thread gelesen. Ein gemeinsamer 1-Tick-Timer schließt fällige Warmups ab: Spawn-Chunk async laden → `beginTeleport` (nur wenn nicht inzwischen abgebrochen) → Standplatz prüfen → `teleport(COMMAND)`. Das eigene Teleport-Event läuft in `COMPLETING`, das nicht abbrechbar ist; das ist der Guard. Ein Listener auf `EntityDamageEvent` behandelt jeden Treffer genau einmal (Abbruch, PvP-Tag über `DamageSource#getCausingEntity`). Cooldown-Persistenz ist Best Effort mit Fail-Closed: die Sperre gilt sofort im Speicher, ein DB-Fehler wird geloggt und beim Disable erneut geschrieben; ein Absturz zwischen Teleport und Commit kann einen Cooldown verlieren. Epoch-Zeit: Uhrsprünge des Servers verlängern bzw. verkürzen laufende Cooldowns entsprechend.
- **Marriage-Herzpartikel**: ein gemeinsamer 20-Tick-Timer iteriert Online-Spieler, behandelt jedes Paar nur von der kleineren UUID aus und liest die Partner aus `MarriageService` (keine zweite Map, kein Schema). Wird in `disable()` abgebrochen.
- **Appearance**: siehe oben; einziger Eigentümer der Teams `illuniumcustom_*` und der vom Plugin gesetzten Tablist-Namen. Ein Spieler, den ein anderes Plugin oder `/team` in ein eigenes Team setzt, verliert dort beim Dekorieren seine Teamzugehörigkeit — Kompatibilität mit anderen Scoreboard-Plugins ist kein MVP-Ziel.

## Security-Grenzen

- Eingaben: Gruppenname/Tag per ASCII-Regex und Länge, Farben aus fester Liste oder `^#[0-9A-Fa-f]{6}$` (nie als MiniMessage interpretiert), Spieler per UUID; Staff-Config nur mit Mojang-UUID (v4) und Profilname. Alle SQL-Statements sind konstante Strings mit gebundenen Parametern.
- Permissions: jeder Spieler-Command prüft `illuniumcustom.use`, `/ic` prüft `illuniumcustom.admin`, `/vanish`/`/unvanish` ausschließlich `isOp()`. Gruppenrollen sind Fachrollen und geben keine Server-Rechte; Staff-Schutz entsteht nur aus `config.yml`.
- Threading: Bukkit-API nur auf dem Main Thread; DB-Arbeit und Profil-Lookups liefern Futures, deren Folgeschritte über `context.mainThread()` laufen und nach dem Disable verworfen werden.
- Fremdes wird nicht gelöscht: nur eigene Teams (Präfix), eigene Rezepte (Namespace), eigene Sitz-Entities (PDC-Tag); Whitelist-Einträge werden nie entfernt.
- Der Guard schützt nicht vor einem böswilligen Operator oder Konsolenzugang.

## Patch v1.3: Datenfluss

- **Leaderboards:** genau elf zentrale Definitionen mit Titel/Einheit/Quelle/Historie. Kandidaten aus `player_profiles`, tatsächlicher Serverhistorie und eigenen Metriken; keine Namensauflösung oder bloßen Whitelist-Kandidaten. Main-Thread-Cursor liest höchstens 32 Blockmaterialien pro Tick und stoppt zwischen Reads nach etwa 2 ms; nicht unterstützte Materialien werden einmalig verworfen. Einzelne Bukkit-Statistik-/Dateizugriffe können länger dauern, weshalb Zielhardware-Profiling ein Release-Gate bleibt. Nur fertige Zahlen verlassen den Main Thread zur Sortierung. Immutable Snapshots bleiben während der TTL-Neuberechnung gültig; aktuelle OP-UUIDs (auch offline) und verborgene UUIDs werden bei jeder Ausgabe ausgeschlossen, danach Wettbewerbsränge gebildet.
- **Playtime:** `PlaytimeReadService.snapshot()` erfasst dieselben noch ungespeicherten Sessionsekunden wie `/playtime` auf dem Main Thread. Ein geordneter Bulk-Read der bestehenden Playtime-Tabelle addiert diese Werte. Vorherige Checkpoints liegen vor dem Read in der DB-Queue. Kein fremder SQL-Write und keine zweite Zeitmessung; bei abgeschaltetem Modul kein Vanilla-Fallback.
- **Custom-Metriken:** `CustomMetricTracker` beobachtet MONITOR-Events ohne Weltaktionen zu beeinflussen. Delta-Batches über die DB-Queue; laufende Batches werden erst nach Commit verworfen, Fehler zurück in den Puffer übernommen. Disable entfernt Listener/Timer und flusht mit begrenzten Wiederholungen. SQLite addiert Zähler atomar und bildet `MAX` für XP. Spawn veröffentlicht nach seinem bisherigen erfolgreichen v1.2-Teleport ein `SpawnTeleportSucceeded` mit UUID/Session-ID; eine separate Unique-Tabelle macht Wiederholung auch nach Restart unschädlich. Keine Spawn-Abhängigkeit auf Leaderboard-Tabellen.
- **Whitelist-Staging:** Repository besitzt nur V4-Tabellen für UUID-Einträge, Launches und Audit. Profilobjekte werden auf dem Main Thread erstellt, ausschließlich die dafür dokumentierte blockierende Paper-Profilvervollständigung läuft in einem begrenzten separaten Pool. UUID/aktueller Name werden aus Mojangs Profil-Property geprüft. `stage` schreibt nur SQLite. `claim` friert alle ausgewählten Zeilen in einer Transaktion als APPLYING ein, bevor irgendeine native Mutation möglich wird. Je Account: Profil revalidieren → native UUID prüfen → Vanilla-Whitelist-Command mit geprüftem, im nativen Cache vorhandenen Namen → native UUID/Name bestätigen → APPLIED/ALREADY_PRESENT committen. Neue Stages gehören nicht zu diesem Snapshot. Teilfehler landen einzeln in FAILED, Retry selektiert nur offene/fehlgeschlagene Einträge.
- **Recovery:** Beim Start werden APPLYING-Zeilen gegen die native Whitelist gelesen: vorhandene Erfolge als APPLIED, fehlende als FAILED; keine neuen nativen Writes. Unterbrochene Launches erhalten PARTIAL. APPLIED/ALREADY_PRESENT werden nie automatisch erneut angewendet. Ein DB-Fehler im laufenden Launch sperrt ihn bis zum Neustart, um nicht vor unbestätigten Claims weiterzumachen. WhitelistGuard behält seine bisherige, getrennte Staff-Policy.

V3/V4 sind additive Migrationen. V1/V2 bleiben unverändert. Die native Whitelist bleibt einzige Zugangsliste; die Staging-Tabellen sind weder Login-Hook noch Reaktivierungsliste.

## Gruppen-Erweiterungen v1.4

`GroupsModule` besitzt `/group`, `/g` und `/gec`; keine zusätzlichen Feature-Module. `GroupService.apply` meldet nach jeder bestätigten Mutation `oldGroup/newGroup` an `GroupChangeListener`, auch wenn die verbleibenden Mitglieder keine Appearance-Änderung benötigen. `/g` liest pro Aufruf die aktuelle UUID-Mitgliedschaft und `VisibilityService`; ausschließlich Text-Komponenten und Online-Empfänger, keine DB oder Chathistorie.

`GroupChestService` hält pro Gruppen-ID eine Session mit genau einem `Inventory` und einem identitätsgeprüften `GroupChestHolder`. Gemeinsame Lade-Future und Zähler wartender Öffnungen verhindern doppelte Inventare oder vorzeitige Cache-Freigabe. Nach dem Laden werden Onlinezustand, Mitgliedschaft, Gruppengröße, Session und Aktivierung erneut geprüft. ItemStack/Inventory bleiben auf dem Hauptthread. Der Entnahme-Modus nutzt eine Allowlist für Klickaktionen und verhindert Drag in obere Slots; unbekannte/bundlebezogene Aktionen bleiben gesperrt. View-Wechsel aus Klick-/Drag-Handlern erfolgen im nächsten Tick.

Schema V5 speichert einen vollständigen, versionierten 27-Slot-Blob mit Leer-/Item-Markern und Paper-NBT pro belegtem Slot, belegten Slots, Revision und Zeitstempel. DB-Queue erhält unveränderliche Byte-Snapshots; Updates vergleichen die vorherige Revision. Nach Events wird im nächsten Tick gespeichert, zusätzlich jede Sekunde verglichen. Letztes Schließen und Disable erfassen den finalen Zustand. Cache-Freigabe erst ohne Zuschauer, wartende Öffnungen, ausstehende Checkpoints oder unbestätigte Revisionen. Fehler behalten die Session und sperren den Zugriff; es gibt keinen leeren Deserialisierungs-Fallback.

Disband reserviert die Gruppen-ID auf dem Main Thread vor dem SQL-Auftrag, damit während des Löschens keine Kiste lädt. Lebende/ladende/fehlerhafte Sessions blockieren beide Disband-Pfade; in der Löschtransaktion wird `occupied_slots` geprüft, zusätzlich schützt ein SQL-Trigger. Nur leere bestätigte Kisten werden per FK-Cascade entfernt. Ein wiederverwendeter numerischer Gruppen-Key erbt keine Items.

`LeaderboardMessageFormatter` formatiert bestehende Snapshot-Zeilen und Navigationsziele. Statistikreader, Repository, Ranking und Cache-Ablauf bleiben unverändert; die allgemeine `Chat.info`-Darstellung bleibt grau.
